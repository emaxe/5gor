# 🚗 План улучшения моделей машин

## 🎯 Цели и приоритеты

1. **Кастомизация игрока** (высший приоритет) — расширить гараж за пределы цвет/диски/спойлер: стиль дисков, боди-кит, декали.
2. **Разнообразие** — больше типов трафика и покупных машин игрока, борьба с «клоновостью» одинаковых силуэтов на улицах.
3. **Детализация** — умеренное усложнение геометрии (зеркала, швы, багажник на крыше, выхлоп) в рамках текущей низкополигональной эстетики.

## 🏗️ Архитектурный подход

Расширяем существующую фабрику `src/carmodel.js`, не переписывая `threeBoxCar`/`boxVanCar`/`CAR_SHAPES`. Силуэты остаются как есть; новые детали и пресеты добавляются как ещё одна опциональная запись в системе `parts: [{g, role}]`, которую `buildCarModel()` уже умеет как сливать в один меш (трафик), так и раскладывать по отдельным мешам (игрок).

**Жёсткое ограничение:** каждая NPC-машина трафика обязана остаться одним `vertexColors`-мешем (1 draw call) — см. `TrafficManager._buildCar()` и `getBodyGeometry()`-кэш в `carmodel.js`. Любая новая геометрия для трафика идёт в `staticColored`/`mergeColored()`, а не в отдельные меши/материалы.

Что **не** входит в этот подход и вынесено в «Вне рамок плана»: смена материальной модели на `MeshStandardMaterial` (металлик/матовый лак), мотоциклы/иная не-4-колёсная техника, экономика продажи боди-китов.

## 🔹 Фаза 1: Кастомизация игрока

**Файлы:** `src/carmodel.js`, `src/config.js`, `src/upgrades.js`, `src/ui.js`, `src/player.js`

### 1.1 Стиль дисков (геометрия, не только цвет)
- В `carmodel.js` добавить варианты сборки диска: `disc` (текущий сплошной цилиндр), `spoke` (диск + 5 тонких радиальных боксов-спиц поверх), `chrome` (текущая геометрия, но с обязательным `matChrome`/светлым цветом вместо `matRim`).
- Добавить параметр `rimStyle` в `buildCarModel(spec)`, влияющий на сборку колеса и для `animated`, и для НЕ-animated веток (спицы должны попасть в `staticColored` для трафика, чтобы не плодить лишний draw call).
- **Механизм переключения (animated/игрок):** все 3 геометрии рима (`disc`/`spoke`/`chrome`) строятся сразу при `_build()` как дочерние меши колеса, ссылки сохраняются как `wheels[i].rimVariants`; `_applyTuning()` переключает между ними через `mesh.visible` — без пересборки геометрии кузова. `chrome` красится материалом `matChrome`, `matRim.color` относится только к `disc`/`spoke`. Геометрия строится по фиксированному энуму `rimStyle`, а **не** итерацией по `TUNING.rims` — `carmodel.js` не импортирует и не должен импортировать `config.js` (фабрика получает всё через `spec`).
- `config.js: TUNING.rims` — заменить/дополнить записи полем `style: 'disc'|'spoke'|'chrome'` рядом с существующим `c` (цвет); это данные для UI-выбора игрока, не источник геометрии.
- `upgrades.js: tuningForCar()` — прокинуть `rimStyle` в объект тюнинга, `save()/load()` уже сериализуют весь `this.tuning` целиком, доп. правок не требуют.
- `ui.js: renderGarage()` (`vкладка tuning`, ряд «Диски») — свотчи дисков дополнить визуальным намёком на стиль (не только цвет заливки).

### 1.2 Боди-кит
- В `carmodel.js` добавить билдер `bodyKitParts(dims, kit)` → `{g, role}[]`: передний сплиттер (тонкий бокс под бампером), пороги (боксы вдоль порогов). Работает по тому же принципу, что уже существующий спойлер в `player.js:_build()` (отдельная группа, `visible` переключается без пересборки геометрии).
- `spec.bodyKit: 'stock'|'sport'` в `buildCarModel`; для игрока — как `spoilerGroup`, отдельная скрываемая группа. **Механизм ссылки:** в отличие от `spoilerGroup` (создаётся прямо в `player.js:_build()`), kit-меши приходят из фабрики (`carmodel.js`) — там же они собираются в одну скрытую группу, ссылка на неё выставляется в `built.refs.bodyKit`; `player.js:_applyTuning()` читает эту ссылку и переключает `visible`. Для трафика — жёстко зашиваем `sport`-кит в 1-2 новых `TRAFFIC_TYPES` (см. Фазу 2) через `staticColored` (участвует в `cacheKey`, см. 2.2).
- `config.js: TUNING` — новое поле `bodyKits: [{name: 'Стандарт', id: 'stock'}, {name: 'Спорт', id: 'sport'}]`.
- `upgrades.js`, `ui.js` — по аналогии с существующим чекбоксом спойлера (`chk-spoiler`) добавить селектор боди-кита в вкладке tuning.

### 1.3 Декали
- Переиспользовать паттерн `makeCheckerStripTexture()` из `utils.js` (уже используется для ливреи такси) — добавить 2-3 генератора текстур: `makeStripeDecalTexture(colorA, colorB)`, `makeRacingDecalTexture()`. Текстуры кэшировать через существующий `_texCache` с ключом, параметризованным по цветам/варианту (по образцу `makeTaxiTexture`: `key = 'taxi_' + colorHex`) — не с фиксированным ключом как у сегодняшнего `makeCheckerStripTexture()`, иначе смена цвета декали не отрисуется.
- **Важно (найдено при разборе плана):** сегодня `built.liveryStripe`-меш строится в `carmodel.js` только при `hasLivery` (условие `if (hasLivery && built.liveryStripe && matLivery)`), а у игрока `hasLivery: !!this.stats.isTaxi` (`player.js`) — то есть anchor для декали физически отсутствует на всех купленных машинах кроме стартовой «Пятёрочки» (`id: 'taxi'`). Фикс: decal-anchor строится для `animated` (игрока) **безусловно**, независимо от `hasLivery`/типа машины. `hasLivery` остаётся отдельным флагом для NPC-трафика (запекание шашечек такси) и определяет **дефолт** декали игрока: `taxi` → дефолт `'checker'` (сохраняет идентичность стартовой машины — иначе игрок молча теряет родные шашечки при первом входе в гараж), остальные машины → дефолт `'none'`.
- `config.js: TUNING.decals: [{id:'none', ...}, {id:'stripe', ...}, {id:'checker', ...}, {id:'racing', ...}]`.
- `ui.js` — новый ряд «Декали» в вкладке tuning.

**Вне рамок:** покраска в металлик/матовый (требует `MeshStandardMaterial`, шире по эффекту на весь рендер-пайплайн игрока) и продажа боди-китов за игровую валюту (сейчас всё в `TUNING` бесплатно и сразу доступно — для v1 сохраняем эту простоту, монетизация — отдельная задача).

**Критерии готовности:** в гараже (вкладка «tuning») можно выбрать стиль дисков, боди-кит и декаль; выбор сохраняется в `localStorage` (через существующий `upgrades.save()`/`load()`) и переживает перезагрузку; смена не требует пересборки всей модели геометрии кузова (только `_applyTuning`-подобный путь для того, что не требует новых мешей).

## 🔹 Фаза 2: Разнообразие

**Файлы:** `src/traffic.js`, `src/config.js`, `src/player.js`

### 2.1 Новые типы трафика
- Добавить конкретно **N=4** новых записи в `TRAFFIC_TYPES` на уже существующих силуэтах `CAR_SHAPES` с новыми габаритами/палитрами/весами (например: `limo` — вытянутый `sedan`, `cab_black` — бизнес-седан с тёмной ливреей, вариация `suv` с иной палитрой). Не создаём новых `CAR_SHAPES`-функций — только новые комбинации существующих. (Сейчас в `TRAFFIC_TYPES` 16 записей — итог после Фазы 2.1: 20, см. поправленный критерий готовности Фазы 3.)
- Проверить, что `TRAFFIC_WEIGHT_TOTAL`/`pickTrafficType()` корректно учитывают добавленные веса (уже общий механизм, правок логики не требует).

### 2.2 Процедурная вариация силуэта (борьба с клоновостью)
- **Канал параметров:** `buildCarModel` сегодня зовёт `shapeFn({w, len})`, а обёртки `CAR_SHAPES` (`threeBoxCar`/`boxVanCar`) не пробрасывают внешние опции. Переписать канал на `shapeFn({w, len, ...opts})`, обёртки — на `(d, o) => threeBoxCar(d, {...base, ...o})` (аналогично для `boxVanCar`).
- В `TrafficManager._buildCar()` добавить **ограниченную дискретную** вариацию 1-2 параметров силуэта на тип, а не случайный float — чтобы `cacheKey` в `getBodyGeometry()` оставался конечным множеством, а не рос неограниченно на каждый спавн. **Вариативные параметры определяются на семейство силуэта, не универсально**: для `threeBoxCar` (`sedan`/`hatch`/`wagon`/`coupe`/`suv`/`retro`/`premium`) — `hoodFrac`/`roofFrac` ±2 шага от базового значения; для `boxVanCar` (`van`/`bus`/`pickup`/`truck` и производные `marshrutka`/`ambulance`/`bukhanka` — 7 из 16/20 типов трафика) `hoodFrac`/`roofFrac` не существуют, там вариация идёт через `cabLenFrac`/`cargoLenFrac`/`cargoH`. Маппинг `variantIdx → параметры` — фиксированный массив 3-5 вариантов **на силуэт**, детерминированный.
- `cacheKey` в `traffic.js:_buildCar()` (сейчас `${def.name}|${bodyColor}`) — переписать не как жёсткий шаблон строки, а как **правило**: `cacheKey` обязан быть детерминированной сериализацией ВСЕХ параметров `spec`, влияющих на `mergeColored()`-выход (включая `rimStyle`, `bodyKit`, `hasRoofRack` из последующих пунктов и `variantIdx` из этого), генерируемой функцией из `spec`, а не собираемой вручную построчно — иначе при добавлении следующего геометрического параметра кэш снова начнёт молча путать геометрии.

### 2.3 Новые покупные машины игрока
- В `player.js: CAR_TYPE_SHAPE` уже импортированы силуэты `sedan/retro/hatch/van/premium` — добавить маппинги для неиспользуемых пока `coupe`, `suv`, `wagon`.
- В `config.js: CARS` добавить 2-3 новые записи (например, `sport` → coupe, `offroad` → suv) с ценой/`unlockRating`, продолжающей текущую прогрессию (после `business`, price > 25000).
- `ui.js` вкладка «cars» уже итерируется по `CARS` — новых правок рендера не требует, только данные.
- **Уточнение по коллайдеру:** `_collide()` в `player.js` использует захардкоженный радиус `r = 2.0` независимо от габаритов машины. Явно принимаем это как общее упрощение для всех типов игрока (альтернатива — вывести радиус из габаритов, `Math.max(2, w*0.6)`, но это отдельная задача вне рамок текущего плана).

**Критерии готовности:** в трафике визуально различимо больше силуэтов/вариаций на глаз при обычной поездке по городу; в гараже доступны для покупки 2-3 новые машины с уникальным силуэтом.

## 🔹 Фаза 3: Детализация

**Файлы:** `src/carmodel.js`

Все пункты — это новые/улучшенные записи в `parts`/`glass`, добавляемые в `threeBoxCar()`/`boxVanCar()` (или отдельным пост-обработчиком `buildCarModel()`, если деталь применима к обеим сборкам). Бюджет: не более **+150-250** треугольников на машину суммарно по всем пунктам ниже (пересчитано от изначальных «10-30» — прикидка по количеству боксов/цилиндров ниже даёт заметно больше; считать по каждой детали отдельно при реализации, чтобы бюджет оставался проверяемым).

- **Зеркала:** заменить нынешний плейсхолдер (`carmodel.js:116`, маленький тёмный бокс) на 2 части — корпус зеркала + ножку крепления, сохраняя тот же anchor-расчёт от `w`/`cabY`.
- **Шов дверей:** тонкая инсетная тёмная полоса вдоль борта кузова (геометрия, не текстура) — по образцу уже существующей боковой окантовки (`chromeTrim`).
- **Багажник на крыше:** новый anchor `roofRack` в `threeBoxCar`/`boxVanCar` (по аналогии с `roofSign`), активен только для `wagon`/`suv`/`van`-силуэтов через флаг `spec.hasRoofRack`.

- Каждая деталь добавляется в `roleParts.dark`/`roleParts.chrome`, то есть автоматически попадает и в статичное слияние (трафик), и в раздельные меши (игрок) без дополнительной ветвления логики.

**Критерии готовности:** новые детали видны на всех 20 типах трафика (16 текущих + 4 новых из Фазы 2.1) и 5(+) машинах игрока там, где применимо; силуэт машины не меняется в габаритах (коллизии/физика не затронуты — за исключением новых типов покупных машин игрока из Фазы 2.3, где коллайдер остаётся общим упрощением `r=2.0`, см. 2.3).

## 🔹 Фаза 4: Проверка производительности и кэша

**Файлы:** нет изменений кода, только верификация.

1. Спавн всех `TRAFFIC_TYPES` (включая новые из Фазы 2) одновременно на сцене — сверить FPS с текущим базовым уровнем на пресетах качества из `CFG_GFX_PRESETS` (`config.js`).
2. Проверить, что `_bodyGeoCache` (`carmodel.js`) не растёт неограниченно из-за процедурной вариации — залогировать размер `Map` после нескольких минут спавна трафика, сравнить с ожидаемым конечным числом `типы × цвета × варианты`.
3. Пройти по всем комбинациям кастомизации игрока (диски × боди-кит × декаль) в гараже — визуально свериться, что смена не роняет FPS и не оставляет утечек геометрии (`_disposeGroup()` в `player.js` уже вызывается при пересборке типа машины — проверить, что он же не нужен при смене тюнинга, раз тюнинг не создаёт новых мешей для параметров из 1.1-1.3).

**Критерии готовности:** количество draw call на NPC-машину не увеличилось; заметных просадок FPS при полном трафике нет.
